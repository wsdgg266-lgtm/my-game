「北近畿で今週なにがあるか」がジャンル別にすぐわかって、
**行きたいイベントのチケットを誰よりも早く取れる**ようにするアプリ。

既存アプリ(かいわすれナシ!・スポカレ!・ふくらぶ!・ピコラン!・ハナビカメラ)と同じ構成で作る:

- ビルド不要・単一HTML(`events/index.html`)・サーバー不要
- PWA対応(ホーム画面に追加してフルスクリーン起動・オフライン閲覧)
- データはブラウザの LocalStorage に保存

### 重点ジャンルの決定が設計に与える影響

選ばれた3系統は**いずれもチケット・申込がからむ**(公演、体験の予約枠、スポーツ大会のエントリー、
企画展の前売券)。一方、祭り・花火・伝統行事は重点から外れた。
つまりこのアプリは **「日程を眺めるカレンダー」ではなく「申込・購入の期限を落とさない道具」**
であることがはっきりしたので、次の方針で作る。

- **発売カレンダーをホームの主役に据える**(単なる日付順の一覧は従)
- 体験・ワークショップやスポーツ大会は「発売」ではなく**「申込受付」**なので、
  `sales` の段階ラベルを **受付開始／申込締切／抽選結果／入金期限** まで扱える汎用の形にする
  (ライブの先行抽選とマラソン大会のエントリーは、構造的にまったく同じもの)
- 祭り・花火・伝統行事のジャンルは**残す**が、データ整備の優先度は下げる
  (年中行事なので後からまとめて入れれば足りる)

## このアプリの一番の売り

イベント情報サイトは既にたくさんある。このアプリの存在価値は**「チケット発売レーダー」**、
つまり *情報を見せること* ではなく **「買い逃さないこと」** に振り切った設計にある点。

人気イベントのチケットを取り逃す原因は、ほぼ次の4つに絞られる。

| 取り逃す原因 | このアプリの対策 |
|---|---|
| **先行受付があったのを知らなかった** | ジャンル別の発売通知。一般発売より前の先行を段階ごとに登録して先に知らせる |
| **発売開始の時間を忘れていた** | 前日・1時間前・10分前の3段階アラート＋カレンダー(.ics)書き出し |
| **発売の瞬間にもたつく** | 発売10分前に「発売ダッシュ画面」が起動。ズレ補正済みカウントダウンと販売ページのボタンを事前に並べておき、0秒で即タップ |
| **抽選に申し込んだ後の期限切れ** | 申込済み／当落発表日／入金期限をステータス管理してリマインド |

**チケットの購入そのものはアプリ内では行わない**(各プレイガイドの規約・認証の都合上、
現実的に不可能)。あくまで **「買う瞬間に最短距離で到達させる」** ための道具として作る。

## データの取り方(方針: 3層構え)

北近畿のイベントを**まとめて配信している公開APIは存在しない**。
また、このアプリはサーバーを持たない静的サイトなので、ブラウザから他サイトを直接読むと
**CORS(クロスオリジン制限)で弾かれる**のが最大の技術リスクになる。
そこで次の3層で組む。

### L1: 内蔵イベントデータ(必ず動く土台)

リポジトリに `events/data/events.json` を同梱し、アプリは**同一オリジンのJSONを読むだけ**にする。

- CORSの問題が原理的に起きない・オフラインでも開ける・表示が速い
- 花火大会や地域の恒例祭りなど**日程が毎年ほぼ決まっているもの**はここに持つのが確実

### L2: GitHub Actions による自動取り込み(CORS回避の要)

**ブラウザではなく GitHub Actions(サーバー側)が外部データを取りに行き、
整形して `events.json` にコミットする**日次ジョブを置く。
push をトリガーに既存の Pages / Vercel デプロイが走るので、サーバーを持たずに
「自動更新されるイベントDB」が成立する。CORSはサーバー側取得なので無関係になる。

取り込み候補(手順0で実際に取れるか検証する):

- **自治体オープンデータ**: 国の「推奨データセット」に**イベント一覧**の標準フォーマット
  (CSV/XLSX)があり、対応した市町なら列構成が揃っている。京都府・兵庫県の市町は
  CKAN ベースのポータル(BODIK 等)で公開しているところがある → **CKAN API で機械取得**
- **観光協会・DMOのRSS/サイト**: 丹後・但馬など。RSSがあれば取り込み、無ければ対象外
- **文化会館・ホールの公演情報**: チケット発売日が載っているのはここ。ジャンル「音楽・ライブ」
  「演劇」の発売レーダーの主要な供給源になる

> 検証で「取れない」と分かったソースは**深追いせず**、L1(手入力)＋L3(リンク)に回す。
> スポカレ!のときと同じ判断基準にする。

### L3: 手動追加とリンク補完(取りこぼしの受け皿)

- ユーザーが自分でイベントを追加できる(名前・日時・場所・ジャンル・発売日・URL)
- 各イベントカードから**プレイガイドの検索結果へワンタップ**で飛べる
  (チケットぴあ / ローソンチケット / イープラス / 楽天チケット / 各主催者サイト)
- 自動取得できなかった公演も「検索して自分で登録 → 発売アラート」の導線に乗せられる

## 画面構成

```
┌──────────────────────────────┐
│ 🎪 キタイベ!        [エリア▾] ⚙ │
├──────────────────────────────┤
│ 🎵 🎆 ⛩ 🏟 🍜 🎨 🎭 🧑‍🍳 👶 🌸  │ ← ジャンル絞り込み(横スクロール)
├──────────────────────────────┤
│  今週末                        │
│  ┌────────────────────────┐  │
│  │🎵 8/22(土) 19:00        │  │
│  │  ○○ホール 開館記念公演   │  │
│  │  福知山市 / 🎟発売中      │  │
│  └────────────────────────┘  │
├──────────────────────────────┤
│ [🏠ホーム][🔎さがす][🎟発売][⭐マイ] │
└──────────────────────────────┘
```

1. **🏠 ホーム**: 今日〜今週末のイベント。上部に「⏰ まもなく発売」を常に固定表示
2. **🔎 さがす**: ジャンル × エリア × 日付 × 「チケット要／不要」で絞り込み。フリーワード検索
3. **🎟 発売カレンダー**: **チケットの発売日順**に並ぶ、このアプリの心臓部。
   先行/一般の段階と受付期間、締切までの残り時間を表示
4. **⭐ マイイベント**: 「気になる」「申込済み(抽選)」「当選・購入済み」「落選」の
   ステータス別。当落発表日・入金期限が近いものを上に出す
5. **🚀 発売ダッシュ**(モーダル): 発売10分前から自動起動するカウントダウン画面
6. **⚙ 設定**: 自分の市町、拡張エリアON/OFF、ジャンル別の通知設定、データ再取得

## 🚀 発売ダッシュ画面(核心機能の詳細)

発売時刻の10分前になると、アプリを開いたときに自動でかぶさる。

- **正確なカウントダウン**: 端末の時計は数十秒ずれていることがある。
  自サイトへの `HEAD` リクエストの `Date` ヘッダーで**サーバー時刻とのズレを測って補正**し、
  「あと 03:41.2」と 0.1秒単位まで表示する
- **販売ページのボタンを事前配置**: 発売開始と同時にタップできるよう、
  プレイガイドのリンクを画面下部に大きく並べておく(0秒での接続を狙う)
- **事前準備チェックリスト**(発売の前日通知と一緒に出す):
  - [ ] プレイガイドの会員登録は済んでいる?
  - [ ] ログインしたままになっている?
  - [ ] 支払い方法(クレカ等)は登録済み?
  - [ ] 枚数・席種・同行者を決めた?
  - [ ] 抽選先行なら申込期間はいつまで?
- **メモ欄**: 会員番号の下4桁、希望席種などを控えておける(端末内のみ)

## ⏰ 通知の設計(iPhone対策が要)

| 手段 | 内容 | 備考 |
|---|---|---|
| **カレンダー(.ics)書き出し** | 発売日時・受付締切・当落発表日を端末のカレンダーに登録 | **これを主軸にする**。iPhone/Android どちらでも確実に鳴り、アプリを開いていなくても効く |
| **アプリ内通知(Web通知)** | アプリを開いている/常駐している間の3段階アラート | iOS Safari は**ホーム画面に追加した場合のみ**Web Push が使える。使えない端末では自動的に.icsに寄せる |
| **バッジ表示** | 「まもなく発売」の件数をタブに表示 | アプリを開いたときに必ず目に入る |

> 通知を .ics 主軸にするのが重要。Web Push だけに頼るとiPhoneで取りこぼす。

## データ設計(LocalStorage)

- `myEvents`: イベントID → ステータス(気になる/申込済み/当選/落選/購入済み)とメモ
- `alerts`: イベントID → 通知設定(前日/1時間前/10分前 の有効フラグ)
- `filters`: 選択中のジャンル・エリア・「チケット要のみ」フラグ
- `settings`: 自分の市町、拡張エリアON/OFF、ジャンル別の通知購読
- `userEvents`: 手動追加したイベント
- `cache`: `events.json` の取得内容と取得日時(オフライン表示用)

## 作る順番(おすすめ)

0. **技術検証**: 北近畿の市町・ホール・観光協会からイベント情報と**チケット発売日**が
   機械的に取れるか確認する。取れないソースは深追いせず手入力に回す。
   **手入力を許容する決定により、この検証は「できたら儲けもの」の位置づけに下がった**ので、
   ここで詰まっても手順1に進んでよい
   → *(注: 現在の作業環境は外部ドメインへの通信が遮断されており、この検証は未実施)*
1. **骨組み**: 画面レイアウト＋ジャンル/エリアの絞り込み。データは仮でよい
2. **イベント一覧・詳細**: `events.json` の読み込み → カード表示 → キャッシュ
3. **🎟 発売カレンダー**: `sales` 配列の表示、発売日順の並び、.ics書き出し
4. **🚀 発売ダッシュ**: 時刻ズレ補正、カウントダウン、リンク事前配置、チェックリスト
5. **⭐ マイイベント**: ステータス管理、当落・入金期限のリマインド
6. **自動取り込み**: GitHub Actions の日次ジョブで `events.json` を更新
7. **仕上げ**: PWA化(オフライン対応・ホーム画面追加)、通知、公開URLの決定

順番の理由: 1〜2は自前データだけで完結するので確実に動く土台になる。
3〜4がこのアプリの存在価値そのものなので、他機能より先に作りこむ。
6の自動化は手動データで形ができてから載せる(自動化が失敗しても手動で運用できる)。

## 実装で仕様から変えた点

- **`imported.json` を分離**: 手で整備する `events.json` と、
  GitHub Actions が自動更新する `imported.json` を別ファイルにした。
  自動取り込みが手入力データを上書きする事故を構造的に防ぐため
- **通知にGoogleカレンダーを追加**: iOS で .ics のダウンロードが
  うまくいかない場合の逃げ道として、URLで開ける Google カレンダー登録も併設した
- **「近くだけ」を車60分圏からブロック隣接に変更**: 所要時間の計算には経路データが要り、
  サーバーを持たない構成では実現できないため、
  「自分のブロック＋隣接ブロック」という近似に置き換えた
